    Foundations

    Everything in CloudCover is built on a few basic ideas. If these are clear, every later stage is easy.

    0.1 Client and server

    A client asks, and a server answers. Your browser is a client. node backend/server.js starts a server. They talk by sending text messages called HTTP requests and HTTP responses.

    0.2 URL anatomy

    http://localhost:3000/api/policies/7/payments?x=1#top
└┬─┘   └───┬───┘ └┬─┘└──────────┬─────────┘ └┬┘ └┬┘

    0.4 JSON

    JSON is the text format the browser and server use to exchange data. It looks like a JS object, but it's just text: {"id":3,"full_name":"Rahul Sharma"}. In JS, JSON.stringify(obj) turns an object into text and JSON.parse(text) turns it back. express.json() does the parsing on the server, and response.json() does it in the browser.

    1.1 The three languages of a page

    HTML: structure (nouns)

    Headings, forms, inputs, buttons. <input id="weight"> creates a box. It doesn't decide how the box looks or what it does.

    JavaScript: behaviour (verbs)

    Stage 3: Single Page App (SPA) and the hash router

    19–28 Aug 2026

    You replaced many HTML files with one index.html. JavaScript swapped the content, so moving between pages never reloaded.

    3.1 Multi-page vs single-page

    Multi-page (Stage 1)

    Click a link → browser asks the server for a new HTML file → whole page reloads, and JS state is lost.

    Single-page (Stage 3)

    Click a link → URL hash changes (#/bmi) → JS router picks a view → only the main area is replaced. Fast and smooth.

    3.2 How the hash router worked (js/router.js)

    User clicks <a href="#/quotes">
    ↓
    Browser fires a hashchange event (no request to the server)
    ↓
    router reads location.hash → "/quotes"
    ↓
    Is "/quotes" in the routes table?
    yes
    ViewQuotes.render() → HTML string
    no
    ViewNotFound (404 view)
    ↓
    main.innerHTML = html, then the view's afterRender() attaches button events

    Each screen was a "view" object in its own file (view-home.js, view-auth.js, view-dashboard.js…). This is exactly what React Router and Vue Router do internally.

    3.3 Lessons from the bug-fix commits

    • Template strings: building HTML with backticks (`<h2>${name}</h2>`). The "fixed quote marks" and "fixed html strings" commits were mismatched quotes inside these.
    • Events must be attached after rendering: an element doesn't exist until its HTML is inserted.
    • Layout: min-height:100vh, flexbox centring and fixing footer height ("fixed screen height bug").
    • Responsive: @media (max-width: …) rules ("made it work on phones").
    Why the current app is differentToday CloudCover has 4 real HTML pages (login, dashboard, portal, auth-callback), and inside dashboard.html the sections are switched by JS (showSection()). That's a mix: separate pages where the security context changes (logged out, office, customer), and SPA-style switching inside each area.
    RememberSPA = one page, JS swaps the content. A router maps URL → view. The hash part of a URL never goes to the server.

    4.2 CORS: the classic first-API problem

    Your page ran on one origin (e.g. 127.0.0.1:5500) and the API on another (…execute-api…amazonaws.com). Browsers block such cross-origin calls unless the API answers with Access-Control-Allow-Origin. The browser first sends an OPTIONS "preflight" request, which is why lambda-sync.js handled OPTIONS.

    Today the frontend and API share one origin (localhost:3000), so cross-origin calls never happen. app.use(cors()) is still present in server.js.

    4.3 Implicit flow (old) vs code + PKCE (now)

    In the implicit flow, Cognito put tokens directly in the URL hash (#id_token=…). They could leak through browser history or extensions. Stage 11 replaced it with the safer authorization code + PKCE flow.

    4.4 SQL vs NoSQL: why you rewrote it

    DynamoDB (NoSQL)

    Great for "get item by key" at huge scale. Joining data (customer → policies → payments) and ad-hoc search are awkward.

    PostgreSQL (SQL)

    Built for relationships: JOINs, constraints, transactions, flexible queries like "all policies due in 5 days with the customer's phone". That's exactly the office's daily question.
    Why throwing it away was rightA prototype answers "can I do this?". Once you understood the real data (customers with many policies, each with many payments), a relational design was the better fit. On 11 Sep you cleared the old files and rebuilt. This is normal and healthy.
    RememberServerless = Cognito + API Gateway + Lambda + DynamoDB, with no server to run. CORS appears when the page and API are on different origins. Relational data belongs in a relational database.

    Stage 5: The database (PostgreSQL)

    database/

    The database is the heart of CloudCover. Everything else is a way to put data in or show it.

    5.1 Atoms: table, row, column, key

    • Table: one kind of thing (customers). Row: one item (Rahul Sharma). Column: one property (pan).
    • Primary key id SERIAL PRIMARY KEY: a unique number per row, assigned automatically.
    • Foreign key customer_id REFERENCES customers(id): a link to a row in another table. The database refuses links to rows that don't exist.

    5.2 The entity–relationship (ER) diagram

    The arrow points from the "one" side to the "many" side. Deleting a customer CASCADES to their policies, investments and login.

    5.3 Rules the database enforces itself

    FeatureExample from schema.sqlProtects against
    NOT NULLfull_name VARCHAR(150) NOT NULLMissing required data
    UNIQUEpan, policy_number, usernameDuplicates (two customers with one PAN)
    CHECKrole IN ('Admin','Staff')Invalid values, even from a buggy server
    REFERENCESpolicy_id REFERENCES insurance_policies(id)"Orphan" rows pointing nowhere
    ON DELETE CASCADEpolicies, investments, accountsLeftover rows after a customer is deleted
    Partial unique indexUNIQUE(cognito_sub) WHERE cognito_sub IS NOT NULLTwo office users linked to one AWS login
    NUMERIC(12,2)premium_amountFloating-point rounding errors on rupees
    Why put rules in the database too?The server validates input, but the database is the last line of defence. Even a buggy controller can't save a duplicate PAN. The server turns the database error (code 23505 = unique violation) into a friendly message.

    5.4 Indexes

    Without an index, finding "policies due soon" means reading every row. CREATE INDEX idx_policies_next_due ON insurance_policies(next_due_date) keeps a sorted lookup, like a book index. Indexes exist on customer_id, next_due_date and policy_id, the columns used in JOINs and the due queue.

    5.5 Trigger: automatic updated_at

    CREATE FUNCTION update_updated_at_column() RETURNS TRIGGER AS $$
BEGIN NEW.updated_at = CURRENT_TIMESTAMP; RETURN NEW; END; $$ language 'plpgsql';

CREATE TRIGGER update_customers_updated_at BEFORE UPDATE ON customers
FOR EACH ROW EXECUTE PROCEDURE update_updated_at_column();

    Before any row is updated, the database itself stamps the time, so no controller can forget.

    5.6 Transactions (ACID)

    A transaction groups queries so they all succeed or none are saved: BEGIN … COMMIT, or ROLLBACK on error. Mark Paid (Stage 7) inserts a payment and moves the due date. You never want one without the other.

    LetterMeaningIn plain words
    AAtomicAll or nothing
    CConsistentRules (constraints) always hold
    IIsolatedTwo users at once don't corrupt each other (FOR UPDATE locks the row)
    DDurableOnce committed, it survives a crash

    6.7 Talking to the database safely

    // ❌ NEVER: user text glued into SQL → SQL injection
db.query("SELECT * FROM users WHERE username = '" + username + "'");
// username = "x' OR '1'='1"  → returns every user!

// ✅ CloudCover: parameterized. Values travel separately from the SQL.
db.query('SELECT * FROM users WHERE username = $1', [username]);
    • Pool (db/index.js): keeps a few connections open and reuses them, because opening a new one per request is slow.
    • DATE as text: types.setTypeParser(1082, v => v) keeps '2026-11-07' as a string. Otherwise JS converts it to a Date at UTC midnight, and with India at +5:30 the date can shift by a day.
    • pool.on('error'): if the DB drops an idle connection, the app logs it instead of crashing.
    • db.transaction(work): BEGIN → your queries → COMMIT, or ROLLBACK on any error, then always release the client.

    7.3 addMonths and month-end clamping

    function addMonths(dateStr, months) {
  const [y, m, d] = dateStr.split('-').map(Number);
  const target = new Date(Date.UTC(y, m - 1 + months, 1));          // 1st of target month
  const lastDay = new Date(Date.UTC(target.getUTCFullYear(),
                    target.getUTCMonth() + 1, 0)).getUTCDate();      // day 0 = last day of previous month
  target.setUTCDate(Math.min(d, lastDay));                            // clamp 31 → 28/29/30
  return target.toISOString().split('T')[0];
}

    Stage 8: Login and security

    middleware/auth.js · authController.js

    8.1 Authentication vs. authorization

    Authentication: "who are you?"

    Password check (bcrypt) → token (JWT) → authenticate middleware. Failure → 401.

    Authorization: "are you allowed?"

    requireAdmin, requireStaff, requireCustomer. Failure → 403.

    8.2 Passwords with bcrypt

    "password123"
    + random salt → slow hash →
    $2a$10$N9qo8u…stored in password_hash
    typed password
    →
    bcrypt.compare(typed, stored)
    →
    true / false
    • One-way: you can't turn a hash back into the password. Even the database owner never sees passwords.
    • Salt: the same password gives different hashes for different users, which defeats pre-computed tables.
    • Slow on purpose (cost factor): a few milliseconds for one login, years for billions of guesses.

    8.3 JWT: the login token

    eyJhbGciOiJIUzI1NiJ9 . eyJraW5kIjoic3RhZmYiLCJpZCI6MSwicm9sZSI6IkFkbWluIiwidHYiOjB9 . 5f3c…
└──── header ───────┘   └────────────────────── payload (base64, readable!) ─────────┘   └ signature ┘

payload = { kind:'staff', id:1, username:'admin_father', role:'Admin', name:'…', tv:0, exp:… }
    • The payload is readable by anyone (it's only base64), so never put secrets in it.
    • The signature = HMAC(header + payload, JWT_SECRET). Changing one letter of the payload breaks it, and only the server knows the secret.
    • exp: office tokens last 10h (a work day), customer tokens 30d (a phone app).

    8.4 The login flow (local mode)

    1Browser → ServerPOST /api/auth/login {type:'staff', username, password} (or {type:'customer', phone, password})
    2Rate limiterThis IP has too many recent failures? → 429 + Retry-After
    3Server → DBSELECT * FROM users WHERE username=$1 (lowercased)
    4ServerNo user, inactive, or bcrypt.compare false → 401 "Invalid login details" (same message for every case)
    5Server → DBUPDATE … last_login_at
    6Server → Browser{ token: signToken({...profile, tv: token_version}, '10h'), user }
    7BrowsersaveSession() → localStorage → redirect by role: dashboard.html or portal.html

    8.6 Instant logout with token_version

    A plain JWT stays valid until it expires, even if you change your password. CloudCover fixes this:

    PC token tv=0
    Phone token tv=0
    → password change / reset / "log out everywhere" / account turned off →
    DB token_version = 1
    →
    old tokens: 0 ≠ 1 → 401
    this device gets a new token tv=1

    Stage 11: AWS Cognito MFA login (authorization code + PKCE)

    22 Oct 2026

    11.1 AWS setup basics

    • AWS CLI + aws login --profile cloudcover: browser-based sign-in. Credentials last 12h and renew for up to 90 days. No access keys in files.
    • Project / account 448592647758, in the new AWS experience. The selected Region is ap-southeast-2 (Sydney). Other Regions, including Mumbai, are blocked by the project's policy, so all Regional resources are in Sydney.
    • The user pool cloudcover-office has MFA required (authenticator app / TOTP). SMS was avoided because of per-message cost and DLT registration in India. Admins create users and there's no public sign-up. Passwords need 12+ characters with mixed types.
    • The app client cloudcover-web is public, with no secret, because a browser can't keep secrets. PKCE replaces the secret.

    11.2 What PKCE is

    PKCE (Proof Key for Code Exchange): the browser makes a random secret (verifier) and sends only its SHA-256 hash (challenge) to Cognito. Later, only someone holding the original verifier can swap the login code for tokens. A thief who steals the code from the URL can't use it.

    11.3 The full sequence

    1login.html → ServerGET /api/auth/config → {provider:'cognito', cognito:{domain, clientId, redirectUri}} (none of it secret)
    2Browserverifier = random 32 bytes, state = random 16 bytes, challenge = base64url(SHA-256(verifier)) → saved in sessionStorage
    3Browser → CognitoRedirect to /oauth2/authorize?response_type=code&client_id&redirect_uri&scope=openid profile&state&code_challenge&code_challenge_method=S256
    4User ↔ CognitoPassword + 6-digit authenticator code on AWS's managed login page (first time: set a new password + scan the QR code)
    5Cognito → BrowserRedirect to /auth-callback.html?code=…&state=…
    6auth-callbackreadCallback(): state must equal the saved state (blocks forged callbacks). Read and delete the verifier.
    7Browser → ServerPOST /api/auth/cognito {code, codeVerifier} (rate limited)
    8Server → CognitoToken endpoint: code + verifier → ID/access/refresh tokens
    9Serveraws-jwt-verify checks the ID token: signature (pool's public keys), issuer, audience = our client, token_use = id, expiry
    10Server → CognitoRevoke the refresh token straight away. CloudCover's own session takes over.
    11Server → DBFind the user by cognito:username. Must exist and be active. First login saves cognito_sub; later logins must match it (a mismatch is audited and gets 403).
    12Server → BrowserCloudCover JWT (10h, with tv) → same session as a local login → dashboard

    11.4 Why hand over to CloudCover's own JWT?

    Roles, is_active, token_version (instant logout) and audit all live in PostgreSQL. Cognito proves identity + MFA, then CloudCover's existing session system handles everything else, so authenticate didn't need to change at all.

    11.5 The on/off switch

    AUTH_PROVIDER=local
    ↓
    Office: username + password/api/auth/cognito → 404
    AUTH_PROVIDER=cognito
    ↓
    Office: "Log in with MFA" onlypassword login → 403, so MFA can't be skipped

    scripts/cognito-add-user.ps1 creates the Cognito user with a temporary password. The username must match the Team page username. docs/aws-cognito-setup.md records every setting, the reason for it, and how to remove it all.

    RememberCode + PKCE: verifier stays in the tab, only its hash is sent. state blocks forgery. The server verifies the ID token, revokes the refresh token, links cognito_sub, then issues CloudCover's own JWT.

    12.4 IAM: who may do what

    Every AWS action needs permission. A role has two policies:

    Trust policy: who can wear the role

    "Principal": { "Service": "lambda.amazonaws.com" },
"Action": "sts:AssumeRole",
"Condition": { "StringEquals":
  { "aws:SourceAccount": "448592647758" } }
    The SourceAccount condition stops other accounts from tricking AWS into using your role (the "confused deputy" problem).

    Permissions policy: what the role can do

    • Lambda role: write its own log group, cloudwatch:GetMetricData, sns:Publish to one topic.
    • Scheduler role: lambda:InvokeFunction on one function only.
    This is least privilege: the minimum needed, so a bug or leak can do little harm.

    12.5 Cost control

    Everything fits in the free allowances (about 30 Lambda runs, 6 metrics, 3 alarms, 1 dashboard). The AWS Budget cloudcover-monthly-50-inr (about $0.60) emails at 50%, 100% and forecast 100%. Every resource is tagged Project=CloudCover so it's easy to find and delete.

    RememberServer → CloudWatch (metrics every 5 min, logs every 1 min) → alarms → SNS → email. Scheduler → Lambda → reads metrics → SNS → 8 AM email. IAM role = trust (who) + permissions (what), always least privilege. No personal data leaves the office.
